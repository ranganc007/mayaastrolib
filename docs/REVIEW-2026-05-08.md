## Performance findings

Each finding is framed as **"in what scenario does this matter,
and to whom?"** per the user's constraint.

### 1. Chart construction baseline: 0.124 ms / chart

**Measured:** 100 default Charts in 0.0124 s.

- **Single-chart usage (CLI tools, occasional API calls,
  notebook exploration):** irrelevant. Charts feel instantaneous.
- **High-throughput scenarios (web request per chart,
  millions-per-day batch):** still good, but watch the per-chart
  setup cost. At 0.124 ms / chart the library can do ~8000
  charts/second on this machine. Well above any realistic API
  load.

### 2. Hidden cost: 33 calc_ut calls per default Chart

**Found:** Default `LIST_OBJECTS_TRADITIONAL` (11 ids) drives
**33** `pyswisseph.calc_ut` calls and 3 `swe_houses` calls. The
extra 22 come from:
- `PARS_FORTUNA` → `pfLon` calls Sun + Moon + houses (3 extra
  calc_ut + 1 sweHouses)
- `SYZYGY` → `syzygyJD` runs ~20-iteration root-finding loop
  (~20 extra calc_ut)

- **For the natal-chart consumer who never reads
  `PARS_FORTUNA` / `SYZYGY`:** invisible — but they pay the
  cost anyway because both are in
  `LIST_OBJECTS_TRADITIONAL`. The cost is 0.124 ms baked into
  every default Chart.
- **For the high-throughput consumer:** drops to roughly
  **0.04 ms / chart** (~3× speedup) by passing
  `IDs=const.LIST_SEVEN_PLANETS` or
  `LIST_MODERN_PLANETS` instead of the default. The library
  already supports this. Documenting it in the README is a
  zero-effort win.
- **For consumers who DO use Pars Fortuna or Syzygy at
  scale:** could be addressed by a single-step root-find
  (Newton / bisection with adaptive step) instead of the
  ~20-iteration coarse loop. Out of scope for this review;
  noted for future.

### 3. Stated inefficiency: `swisseph.fixstar_mag` parses `fixstars.cat` on every call

**Found:** `mayaastrolib/ephem/swe.py` carries the comment
*"swisseph.fixstar_mag function is really slow because it
parses the fixstars.cat file every time"*. Default
`LIST_FIXED_STARS` has 35 entries; calling `chart.getFixedStars()`
costs ~1.47 ms total because of 35× file parse.

- **For consumers who never call `getFixedStars()`:**
  irrelevant. It is lazy by design and not invoked during
  default Chart construction.
- **For consumers who call `getFixedStars()` once per chart in
  a batch loop:** 1.47 ms / chart, ~12× the rest of chart
  construction. Becomes the dominant cost.
- **For consumers who pre-cache and lookup individual stars:**
  also 1.47 ms / star query.
- **Fix shape:** memoise `swisseph.fixstar2_mag(star)` at
  module level. The mag is a static property of each star —
  no time-varying input. One-line `@functools.lru_cache`
  around the wrapper. Removes the only documented "really
  slow" path in the codebase.

### 4. Allocation in `Chart.profected()`: 27 fresh Objects

**Found:** `Chart.profected()` rebuilds objects, houses, angles
via `with_longitude(...)` — 11 + 12 + 4 = 27 new instances
per profected chart.

- **For consumers building a single profected chart:** 27
  allocations is invisible.
- **For consumers building a profection table for ages
  0–80:** 81 charts × 27 allocations ≈ 2,200 instances. Still
  microseconds at Python's allocation rate; not the bottleneck.
- **For consumers building a profection table for every day
  of a year (rare but possible for sub-year profections):**
  tens of thousands of instances. Worth an
  `Object.replace_lon_inplace()` escape hatch for the hot
  path — but no consumer has reported pain. **Defer.**

### 5. `_DualAccess` wrapper allocation per property access

**Found:** Task 006's `property_with_method_compat` decorator
returns a fresh `_DualAccess` wrapper on every read of
`obj.movement`, `obj.gender`, etc. (Task 010 added a `None`
passthrough for symbolic objects, but real values still
allocate.) Negligible per access.

- **For typical chart-rendering or interpretation flows:**
  invisible.
- **For dignity-heavy loops where every planet's `gender` /
  `faction` / `element` / `movement` is accessed many times
  per scoring run** (`accidental.py::getScoreProperties`):
  measurable but small. Hard to justify acting on now.
- **In 1.0:** `_compat.py` and the entire `_DualAccess`
  apparatus go away. The wrapper allocation goes away with it.
  No need to fix-then-remove.

## Reliability and test gaps

1. **`tests/golden/` directory does not exist.** `CLAUDE.md`
   mandates two test layers (structural + golden / functional)
   "both mandatory." Coverage gate enforces structural; there
   is no astronomical-correctness anchor. Every refactor since
   Task 005 has been verified against itself. Real risk going
   into Phase 2 (Vedic) where ayanamsa application is testable
   against published reference charts. **This is the headline
   reliability gap.**
2. **`GeoPos` input validation is missing.** Probe:
   `GeoPos('200n00', '0w00')` returns `lat=200.0` without
   raising. The library's defenses against bad input are
   accidental (`int()` cast on `"garbage"` happens to raise
   `ValueError`, `swisseph.calc_ut` raises on unknown bodies)
   rather than explicit. A few `if not -90 <= lat <= 90: raise
   ValueError(...)` checks at the constructor would be a small
   improvement.
3. **`protocols/temperament.py` and `dignities/accidental.py`
   have only smoke-test coverage** of individual factors. Each
   is a multi-rule scoring engine; per-factor unit tests would
   catch a future regression without much effort.

exploit path through accepting 200° latitude, just a wrong
calculation.

session is achievable for someone who already knows their
reference, but two is the honest default.

- **Type hints on the public API surface.** `chart.py`,
  `object.py`, `datetime.py`, `geopos.py`, `aspects.py`.
  Pre-PyPI-release hygiene.
- **Split `dignities/accidental.py`** along the natural
  rule-family seams (sun-relations, light, orientality, haiz,
  scoring). Or — better — extract the scoring rules to a data
  table. 480 LOC, 47 methods, one class.
- **Pars Fortuna and Syzygy in the default object list.**
  These two account for 22 of the 33 `calc_ut` calls in
  default Chart construction. They may not belong in
  `LIST_OBJECTS_TRADITIONAL` by default — most consumers
  don't use them. Investigate whether the default should
  exclude them, with opt-in via a separate list constant. Do
  NOT pursue a `lazy_extras=True` constructor flag without
  understanding the downstream coupling first (Syzygy is
  referenced from dignity / lot computations; Pars Fortuna
  similarly; a lazy flag changes API behaviour between
  equivalent charts). If they stay in the default, the
  ~20-iteration `syzygyJD` root-find in `ephem/tools.py`
  could collapse to a 3–4 step Newton — but only worth doing
  if the default-list answer keeps Syzygy.
- **`AccidentalDignity.getScoreProperties` rule extraction.**
  88 LOC of dict-assembly. Each rule is a `(condition, score,
  key)` tuple; one loop and a data table replaces the
  function.
- **`_DualAccess` removal in 1.0.** The wrapper exists only
  to support the deprecated method-style access for
  property-converted methods. When the deprecation lands, the
  wrapper goes — and so does the per-access allocation.
- **Per-factor unit tests for `temperament.py` and
  `accidental.py`.** Both are smoke-tested only today.
